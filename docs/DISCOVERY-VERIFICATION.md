# Listening-reference discovery — 0.2.4

## Findings

The previous parser marked any mention of “recently played” or listening history as a direct history request. “More music just like my recently played tracks” therefore skipped inference and catalogue discovery and replayed the available recent list. That list can contain repeated plays of one track; final validation rejected those as accidental duplicates. The same message could also occur when the model selected duplicate candidate IDs. This was routing and duplicate-handling behavior, not evidence of the model successfully trying and failing to discover similar music.

## Changes

- Distinguish direct replay from music inspired by recent or locally most-played songs. Explicit history references work in a fresh session and do not require a prior Queue Companion selection. Playlist names remain data rather than triggering history commands.
- Deduplicate available references and choose up to 12 with artist variety spread across the available history. Artist searches sample across those references rather than taking only the newest artists. Search up to four reference artists in parallel for a bounded initial pool. Interleave the chosen artists in the final discovery queue. Request the complete primary-plus-reserve proposal budget explicitly. Send compact title/artist references separately from queue candidates. The model infers musical compatibility and is instructed to include related artists beyond the seed artists, subject to narrower user constraints. These are inferred musical judgments, not measured genre/audio-feature claims.
- Exclude all available reference songs, matching remastered/mono/stereo album editions, current tracks, and pending append tracks. More requests exclude the previous selection. Source replacement can reuse tracks from the queue being replaced; fresh source membership is still verified. Live/acoustic/remix title variants remain distinct.
- Preserve all valid model proposals through parsing, then remove duplicate IDs, URIs and song identities on the client and fill from available reserves. Unknown IDs are still rejected, including unused extras. Responses above the absolute 200-proposal safety limit are rejected. Completed valid proposals are capped at the requested target-plus-reserve budget after all IDs and source restrictions have been checked; malformed song entries are discarded with diagnostic counts. Restricted-source discovery never accepts catalogue suggestions.
- Remove repeated/familiar suggestions before exact Spotify lookups. Resolve and validate in bounded batches of ten rather than five, preserving order. Four artist searches run concurrently. There is still one inference call, no automatic inference retry and one reconciled native queue write.
- Keep intentional repeat requests working while negated phrases such as “no duplicates” and “do not include duplicates” disable repeats. Direct recent replay deduplicates history before taking the requested count.
- Use `reasoning.effort=low` for the documented GPT-6 Luna/Sol/Astra and GPT-6.1 Sol families in ChatGPT requests. Other model choices retain their original request contract. Official OpenAI documentation states that these families support low effort and GPT-6 Luna defaults to medium: [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning), [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist). Low effort aims to reduce inference latency; live measurements are needed to assess the effect in this workload.
- Check the Spotify account around history retrieval and before sending references to inference. Record retrieval, resolution and validation timing alongside the existing in-memory result; no new prompt or credential log is created.

## Automated verification

All 109 checks passed: 44 extension tests, 44 helper/installer tests and 21 browser UI checks across four viewport sizes. TypeScript checking and bundling succeeded. Helper tests use isolated fake credentials and HTTP stubs. The GPT-6 contract test verifies low effort, one inference, streaming and no server-side storage; an unknown test model receives no reasoning parameter.

New checks exercise the user's exact prompt on a fresh session, different-song discovery and related-artist suggestions, seed exclusions before lookups, alternate editions, source-restricted inspiration, most-played inspiration, empty-history failure, replay deduplication before trimming, recoverable duplicate candidate IDs, explicit source replacement, bounded diverse references and repeat negation. Native availability checks prove ten concurrent requests at most, one request per track and unchanged output order. History account changes abort before inference, and retrieval remains capped at 200 raw entries. Provider parsing bounds seeds separately from candidates and retains valid duplicate proposals for client recovery.

The earlier seven-failed-match reserve regression and native queue reconciliation/source membership/cancellation tests still pass. See `SELECTION-VERIFICATION.md` for the prior 0.2.3 findings and observations.

## Live verification

Verified on the existing Windows desktop Spotify Premium 1.3.4.258 installation using the connected ChatGPT `gpt-6-luna` model. The exact prompt “more music just like my recently played tracks” selected 50 playable tracks for a target of 50, across 10 artists. None matched the 47 unique songs available in the recent-history response; 9 tracks were by artists outside that entire recent list. Twelve spread taste references and four parallel catalogue searches supplied a pool of 81 candidates. This confirms discovery beyond the replay list, not a guarantee that none were ever heard outside Spotify's available history.

The final low-effort run took 14,881 ms overall, with 11,498 ms in inference, 664 ms in retrieval, 1 ms in suggestion processing and 1,843 ms in availability checks. It used suitable resolved candidate IDs, so no suggestion searches were needed in that run. The completed model answer supplied 25 extra valid proposals beyond the 75-choice budget; these were capped safely before selection. One inference was made, and the read-only verification writer performed no native queue mutation. Current track identity and manual queue entries were unchanged. See `discovery-inference-live-proof.json`.

The earlier run with the same spread references and default model effort took 29,525 ms overall, including 22,348 ms in inference, and also selected 50 distinct playable tracks. This is a pair of live observations, not a statistical latency guarantee; generated recommendations and provider latency vary. The first low-effort attempt exposed a model count/format error that the original strict parser rejected. The final parser's bounded recovery is covered by tests and the successful live run. Musical relevance was reviewed against the listening references; no automated genre-perfectness claim is made.

The final 0.2.4 installer upgraded successfully. Settings and pairing remained byte-identical, and the existing protected ChatGPT connection stayed usable. Credential bytes changed during live authentication, consistent with renewable credentials rather than a lost connection; no plaintext credential was inspected or copied into the proof. See `discovery-upgrade-proof.json` and `discovery-private-preservation.json`. The installed production helper and staged extension match the release build after removal of temporary live-test instrumentation. No private listening audit or temporary test bundle is included in the distribution.

Live Claude inference and the second Windows-account installation remain pending from earlier releases. Both providers share the reference instructions, proposal normalization and final client selection safeguards; Claude coverage for this change uses isolated API stubs.
